# 宿舍公共物品借还小站：三 Agent 协作操作手册

> 归档分类：case0。由于项目规模太大，本次不作为 pre 展示项目。以下保留原流程作为参考；当前展示选择见 [docs 总说明](../README.md)。

本文是一份待执行的开发与演示流程。尚未生成项目代码，也未验证下面的业务结果。旧案例文档保留，本次只使用这一份。

## 1. 这次做什么

做一个本地网页，管理宿舍共用的雨伞、工具箱和打气筒。用户可以查看物品、借用、归还；提供者可以管理物品；生活委员可以查看借用记录，第二轮再增加损坏登记。

最终有三个页面入口：借用同学、物品提供者、生活委员。它们属于同一个应用，读取同一份数据库。

范围固定：

- 三件初始物品，两个固定演示借用人“小林”“小周”。
- 一件物品代表一个实物，同一时间只能有一条未归还借用记录。
- 使用本机 Node.js、原生 HTML/CSS/JavaScript、SQLite；不安装前端框架。
- 不做真实登录、权限系统、预约、审批、支付、通知、上传图片或部署。
- 页面切换演示身份不等于真实权限保护。本项目是课堂原型。
- 数据保存在项目内，刷新网页或重启服务不会丢失。

三个用户的独立需求：

- Alice 代表借用同学：方便借东西、看到自己借了什么、能够归还。
- Bob 代表物品提供者：登记和维护自己的物品、控制是否继续出借。
- Carol 代表生活委员：了解公共物品流转，后续处理损坏与修复。

每个 Agent 都完成自己业务的页面、接口和测试。Bob 额外维护公共启动入口与数据库文件，不拥有改变其他用户需求的权力。

## 6. 第一轮：手动跑通正常借还

用公共雨伞测试，不必让 Bob 再添加一把同名雨伞：

1. 在物品提供者页面，确认公共雨伞存在并允许出借。
2. 在借用页面选择“小林”，借用公共雨伞。
3. 切换“小周”，确认无法再借同一把雨伞。
4. 在生活委员页面，确认出现小林的未归还记录，未归还件数正确。
5. 在提供者页面暂停这把雨伞出借。
6. 回到小林，归还雨伞；归还应成功。
7. 切到小周，确认雨伞仍不可借，不能因归还自动恢复提供者已暂停的出借意愿。
8. 提供者恢复出借后，小周可以借用；完成后由小周归还，为第二轮准备空闲物品。
9. 刷新页面，确认历史记录仍在。
10. 可在服务终端按 Ctrl+C 正常停止，再执行 node server.mjs，确认历史记录保留、初始物品没有重复出现。

仅用页面顺序操作不能证明并发安全。重复借用的服务端限制、同时请求的行为，应看实际自动测试或专项验证记录。

如某一步失败，把操作和实际现象反馈给负责成员，修复后重新验证受影响流程。

### 正确实现应保留的区别

供操作者验收，不必提前把实现答案发给三个助手：

- 是否仍在借用：由未归还记录表达。
- 提供者是否允许出借：由提供者的设置表达。
- 是否损坏：由维护状况表达。

这三项可以同时存在。可借条件应同时满足“无未归还记录、提供者允许出借、物品未损坏”。具体字段如何设计由助手协商，不强制字段名。

## 8. 第二轮：重启并验收

代码更新后，先让 Bob 完成第二轮整合检查。然后在原服务终端 Ctrl+C，再执行 `node server.mjs`，让后端加载新代码。不要启动两个同端口服务，不要删除数据库来绕过迁移问题。

浏览器刷新三个页面，按顺序操作：

1. 确认雨伞已归还、未损坏、提供者允许出借。
2. 小林借走雨伞。
3. Carol 对应的生活委员页面登记损坏，说明填写“伞骨松动”。
4. 检查记录仍显示小林持有雨伞，没有凭空归还或丢失借用人。
5. 小林归还成功。
6. 小周仍不能借用，页面说明损坏原因；服务端也应拒绝新借用。
7. 生活委员标记修复，小周现在可以借用；随后归还。
8. 提供者将雨伞设为暂停出借，再登记损坏并修复，确认它仍然暂停出借。
9. 检查第一轮的历史记录仍然存在。

任意成员说“完成”都不能替代这一轮实际操作。每项分别记录通过、失败或未验证。

建议先完整开发、排练并录制。现场不要从零等待三个 Agent 写完整项目。准备一个 3–5 分钟的讲解版本，耗时按排练结果调整。

### 第一段：三个用户、同一个小项目

打开首页说明：借用同学要方便借还，提供者要控制出借，生活委员要管理记录。三个助手各自完成页面、接口和测试。

### 第二段：展示基本成果

借出一件物品，切换用户看不可重复借用，再看生活委员的记录。用网页证明系统有真实数据流，而不只是聊天。

### 第三段：展示协作证据

从真实记录中展示：

- 你只向 Carol 提出损坏需求。
- Carol 向其他成员发送需求，双方讨论怎样保留原来的借用与暂停规则。
- Alice、Bob 各自更新自己负责的模块，并返回测试结果。

可播放真实排练录像，标明是录制片段，不伪造“秒完成”的现场过程。

### 第四段：展示变更后的效果

重点演示“借出→损坏→归还→仍不可借→修复后可借”。这段最容易让观众理解：损坏登记不是只多一个按钮，它影响借用规则、记录和页面显示，必须由多个成员协调完成。

可以这样讲：

> 三位用户各自有需求。新增损坏管理时，生活委员的助手需要让借用端和设备管理端理解新规则，同时不能破坏其他用户原有要求。我们通过 Team Hub 交换需求、协商公共数据并分别实现，最后用同一个网站验证结果。

被问“为什么不用 subagent”时，说明本案例展示多用户独立会话与需求更新，不主张其他代理组织方式绝对做不到。

## 10. 遇到问题怎么处理

- **回复固定、不执行任务：**检查是否处于离线体验，切换到真实 API 模型。
- **停在待审批：**核对并处理操作申请。
- **等不到消息：**确认对方实际发送成功，再手动推动接收方下一轮。
- **三方接口不一致：**让 Bob 汇总具体差异，通过 Team Hub 协商并更新公共约定，不让三个助手各改一套公共结构。
- **改动后网页没变化：**刷新页面；后端代码变更后重启本项目服务。
- **缺少文件或模块：**反馈给对应文件负责人，不能靠改启动命令掩盖未完成的整合。
- **数据库报错：**保存错误，交给 Bob 处理兼容；不要直接删库，会丢失演示证据。
- **测试把示例数据清空：**停止继续验收，检查测试是否错误使用了演示数据库。后续测试改用隔离数据库。
- **同一文件修改冲突：**按文件分工协调，不能据此宣称现有 hook 已提供可靠锁定。

## 11. 最后需要保留什么

- 项目源文件、启动说明和数据库迁移说明（如有）。
- 三个用户的任务及真实消息往返。
- 公共接口约定，以及第二轮修改了哪些约定。
- 实际测试命令、输出与未验证项。
- 正常借还和损坏流程的截图或录像。
- 明确记录：哪些步骤由人审批、推动收信、重启和验收。

你现在的第一步：创建空项目文件夹，让三个窗口都选中它，然后按第 3 节分别发送任务。
