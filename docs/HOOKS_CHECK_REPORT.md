## 1. 结论

基础任务登记、消息注入和状态更新逻辑通过隔离验证，但修改检查和冲突检测存在漏报、误报。

- 仓库原有测试：4 项通过，0 项失败。
- 追加隔离检查：25 项，其中 15 项符合预期、10 项不符合预期。
- 10 个不符合预期的检查集中于下文的 5 类问题，并非 10 个独立缺陷。

目前可以继续用它演示协作流程，但不宜把这些检查视为完整、可靠的防冲突保障。

## 2. 测试方法与边界

### 已执行的方法

1. 在仓库运行 `npm.cmd test`，确认原有 4 个测试通过。
2. 通过 Node.js 和 `tsx` 在内存中运行额外诊断，直接导入 `src/hook.ts` 中的 `runHook`、`patchPaths`，以及现有服务与存储实现。
3. 每组隔离场景新建 `TeamHubStore(":memory:")` 和监听本机随机端口的 Team Hub 服务，通过真实 MCP 连接调用 hook 逻辑；场景结束后关闭服务和数据库。
4. 服务不可用场景通过子进程运行已编译的 `dist/hook.js`，连接本机未监听端口，检查退出码及标准输出。
5. 检查结束时，Git 工作区仍无源码变更。本报告是在检查完成后另外新增的文档。

### 没有做的事情

- 没有调用 DeepSeek 或其他模型 API。
- 没有连接现有 7878 服务进行消息测试，也没有读取、消费原有协作消息。
- 没有实际执行诊断输入中的写文件、删除、安装或 Git 推送命令；这些命令仅作为字符串传给 `PreToolUse` 判断。
- 没有在本轮重新操作三个真实 Codex 对话，验证所有事件是否确实由客户端触发。
- 没有抓取本机 Codex 0.164.0 的真实 hook 输入。补丁字段兼容检查依据当前官方文档构造输入，其对该版本真实会话的影响仍需核对实际载荷。
- 临时诊断通过进程输入执行，没有加入仓库测试文件；本报告保存了场景和结果，未保存完整诊断脚本。

因此，“hook 处理模拟事件正常”和“真实客户端会正确触发该事件”应分别验收。

## 4. 问题详情与复现条件

以下代码位置以提交 `cf9dadc` 为准。

### 问题 1：补丁位于 `tool_input.command` 时，路径解析为空，冲突漏检

**建议优先处理。**

位置：`src/hook.ts:210`，`patchPaths()`。

当前实现仅从 `toolInput.input` 或 `toolInput.patch` 获取补丁文本。当前 Codex 官方文档说明，`apply_patch` 的 hook 输入使用 `tool_input.command`。

参考：<https://learn.chatgpt.com/docs/hooks>，PreToolUse / PostToolUse 输入字段说明。

复现条件：

1. 在内存服务中注册 Alice、Bob，分别创建当前任务。
2. 两者使用相同工作目录，均声明计划修改 `add.mjs`；任务摘要已填写，状态为 `working`。
3. 使用下面的补丁文本，分别放到 `tool_input.input` 与 `tool_input.command` 中调用 Alice 的 `PreToolUse`；`tool_name` 为 `apply_patch`。

```text
*** Begin Patch
*** Update File: add.mjs
@@
-old
+new
*** End Patch
```

预期：两种输入在解析后应指向同一文件，冲突应被阻止；至少应支持客户端实际使用的字段。

实际：

- `patchPaths({ command: patch }, cwd)` 返回 `[]`，没有提取到 `add.mjs`。
- 使用 `tool_input.command` 时，`PreToolUse` 返回 `{}`，未阻止冲突。
- 对照组使用 `tool_input.input` 时，正确返回 `decision: "block"`，原因包含 Bob 的路径冲突。

影响：若真实客户端使用文档中的字段，补丁路径冲突检查会漏检。缺少工作摘要时的阻止逻辑仍能生效，不能将两种检查混为一谈。

待补证据：捕获实际 Codex 0.164.0 的脱敏 hook 输入，确认该版本的补丁字段。

### 问题 2：多种 Windows 修改命令未被识别，跳过工作计划检查

**建议优先处理。**

位置：`src/hook.ts:256`，`mutatesWorkspace()`。

复现条件：

1. 为 Alice 创建任务，仅登记原始意图，尚未填写 `intent_summary` 和 `planned_paths`。
2. 以 `tool_name: "Bash"` 调用 `PreToolUse`，分别将以下字符串放进 `tool_input.command`。

```powershell
Set-Content -LiteralPath add.mjs -Value changed
'changed' | Out-File add.mjs
Remove-Item -LiteralPath add.mjs
node -e "require('fs').writeFileSync('add.mjs','changed')"
npm.cmd ci
```

预期：这些操作均可能修改工作目录；按照“修改前报告计划”的目标，应提示补齐状态或阻止继续。

实际：5 种输入均返回 `{}`，没有阻止。

对照：同样没有摘要的 Alice 执行 `apply_patch` 检查时，正确返回 `decision: "block"`。

影响：现有命令正则只覆盖部分语法，无法保证所有写入行为都先登记计划。Windows 使用的 `npm.cmd` 与 PowerShell 文件操作尤其容易落在覆盖范围之外。

说明：以上命令没有实际执行。应与队友确认检查的目标覆盖范围；简单增加几个关键词也不能保证识别任意脚本的全部副作用。

### 问题 3：不同独立工作目录中的同名文件被误判为冲突

位置：`src/hook.ts:396`，补丁路径冲突筛选。

复现条件：

1. Alice 工作目录为 `C:/Users/LENOVO/teamhub-lab/workspaces/alice`。
2. Bob 工作目录为 `C:/Users/LENOVO/teamhub-lab/workspaces/bob`。
3. 两者为独立目录，均声明计划修改相对路径 `add.mjs`，摘要已填写。
4. 使用程序目前能解析的 `tool_input.input` 提交 Alice 修改 `add.mjs` 的补丁，单独验证路径比较逻辑。

预期：独立目录中的两个同名文件不应仅凭文件名就判定为同一文件。

实际：返回 `decision: "block"`，提示与 Bob 的活动工作重叠。

原因：比较相对路径前没有限定仓库或工作目录，也没有按各成员自己的目录统一解析其路径。

影响：成员使用独立副本时，可能被与自己无关的文件计划阻止。

备注：若产品希望将同一逻辑仓库的不同副本也视为协作冲突，应先定义共享仓库身份；不能直接把所有目录中的同名文件都视为冲突。

### 问题 4：离线成员的未过期计划仍然阻止修改

位置：`src/hook.ts:396`；相关状态筛选在 `src/store.ts:396`。

复现条件：

1. Alice、Bob 使用同一工作目录，均有当前任务和计划路径 `add.mjs`。
2. Bob 状态设置为 `offline`，其状态记录尚未过期。
3. Alice 以 `tool_input.input` 提交修改该文件的补丁。

预期：如果 `offline` 表示不再持有活动工作，Bob 不应继续占用该路径。

实际：Alice 仍被阻止，原因仍是与 Bob 的活动工作重叠。

原因：`getActiveStates()` 按过期时间筛选；补丁冲突筛选没有进一步排除离线状态。

影响：成员退出后，其残留计划可能在过期前继续阻止其他成员工作。

建议先确认状态语义：如果设计上需要退出后保留占用，需要明确释放方式；否则应调整冲突参与状态。

### 问题 5：不同仓库的同名分支被误判为推送冲突

位置：`src/hook.ts:419`，推送分支检查。

复现条件：

1. Alice、Bob 分别登记两个不同的仓库标识，例如 `C:/unrelated-a`、`C:/unrelated-b`。
2. 两者分支均为 `main`，Bob 状态为 `working`。
3. 为 Alice 的 `PreToolUse` 提供命令字符串 `git push origin main`。

预期：不相关仓库的同名分支不应直接形成推送冲突。

实际：返回 `decision: "block"`，提示 Bob 正在同一分支工作。

原因：条件比较了分支名和工作状态，没有先比较仓库身份。

影响：常见的 `main` 分支名可能导致无关项目互相阻止。

说明：使用的是合成状态与命令字符串，没有创建测试仓库，也没有执行真实推送。

## 5. 尚未覆盖或需要单独确认的事项

- 本机 Codex 0.164.0 实际传入的 hook JSON，尤其是补丁字段及工具名称。
- 在真实 UI 中中断、退出后，客户端是否及时触发相应事件；本轮只验证处理函数收到事件后的状态变化。
- 网络连接卡住时的超时行为。本轮故障场景为本机端口未监听、连接失败，不代表所有网络故障场景。
- 并发操作竞态、原子锁定和真实 Git 推送协作。本轮没有验证，也不应据此声称已有可靠锁机制。
- 长消息截断、状态 TTL 到期边界等其他场景未在这 25 项检查中覆盖。

## 6. 当前自动化能力的准确描述

当前实现可以在用户提交新任务时登记意图，并读取消息放进模型上下文；工具调用前后及会话结束时执行相应检查或状态更新。

它没有实现“收到消息就自动唤醒空闲助手”，也不是后台持续轮询收信。因此，人工发送下一条任务或“继续”以触发新一轮，并不代表 hook 接入失败。

## 7. 建议的后续顺序

1. 先确认真实 Codex hook 输入格式，处理补丁字段兼容问题。
2. 明确并完善 Windows 修改操作的检查覆盖范围。
3. 明确仓库、工作目录和分支的冲突范围，避免无关项目误报。
4. 明确 `idle`、`interrupted`、`offline` 是否继续持有文件计划，以及释放方式。
5. 将确认的复现条件补入正式回归测试，再进行真实三助手联调。

以上是修复建议，本轮未实施任何源码修复。

## 8. 补充：双成员并发冲突实验

### 方法

在上述检查后，另做了一组双成员并发实验：

- 每个场景建立独立内存数据库和随机端口服务。
- 为 Alice、Bob 准备虚构的任务状态。
- 同时启动两个独立 Node.js 进程，分别运行现有 `src/hook.ts`，通过各自的 MCP 身份执行 `PreToolUse`。
- 每类场景重复 3 次，共 6 类、18 次成对检查；每对进程的运行时间均有重叠。
- 这里模拟的是两个成员并发请求 hook 判断，不是启动两个真实模型会话。补丁格式与修改计划由诊断程序构造。
- 除下面单独说明的一次临时文件写入外，其余场景仅检查 hook 决策，没有实际执行补丁或写入。

临时结果目录：`C:\Users\LENOVO\AppData\Local\Temp\teamhub-concurrency-7b1p2v`。原始观察结果保存在其中的 `results.json`；此临时路径仅在测试电脑上有效，转发本报告无需包含该目录。

### 结果

1. **同一目录、同一文件，补丁放在 `tool_input.input`：**3 次都是双方被阻止，正确发现了冲突。它不会自动选出先执行的一方，需要后续协调。
2. **同一目录、同一文件，补丁放在 `tool_input.command`：**3 次都是双方被放行，漏检冲突。该字段符合当前官方文档，但真实 Codex 0.164.0 的载荷仍需单独捕获确认。
3. **同一目录、不同文件，使用 `tool_input.input`：**3 次都是双方被放行，符合预期。
4. **两个独立目录、同名文件，使用 `tool_input.input`：**3 次都是双方被阻止，发生误报。
5. **同一目录，分别使用 `shared.mjs` 和 `SHARED.MJS`：**先确认本机临时目录中的这两个名字指向同一个文件；使用 `tool_input.input` 后，3 次都是双方被放行，漏检 Windows 文件名大小写导致的实际冲突。这是本次并发检查额外发现的问题。
6. **双方都未填写工作摘要，用 PowerShell 修改同一文件：**分别提交 `Set-Content` 写入命令，3 次都是双方被放行，未执行预期的修改前计划阻止。

按上述预期判断，18 次成对检查中 6 次符合预期、12 次不符合预期。这是针对边界条件的定向测试，不能当作产品整体成功率。

### 实际临时文件覆盖验证

在第 6 类的第一次测试中：

1. 临时 `shared.mjs` 初始内容为 `export const value = 0;`。
2. 两个 hook 并发检查，均返回 `{}`，没有阻止。
3. 等两份判断均返回后，启动两个 PowerShell 进程并发写入同一个临时文件：Alice 写入值 `1`，Bob 写入值 `2`。
4. 两个写入进程均以退出码 0 完成。
5. 最终文件内容为 `export const value = 2;`，Alice 的值未保留。

这表明：至少在该可复现执行顺序下，hook 没有阻止有冲突的写入，后一次写入覆盖了前一次结果。最终保留哪一方取决于执行顺序，不能保证每次都是 Bob。

两个 PowerShell 进程的标准错误流中出现了模块初始化的进度记录（CLIXML），并非失败结论；上述成功判断依据退出码和最终文件内容。

实际写入仅发生在新建的临时目录。没有修改仓库源码、三个助手已有的工作文件、配置或正式 Team Hub 数据库，也没有调用付费模型。

### 并发检查结论

当前实现能够识别部分冲突，但不能可靠判断所有双成员并发修改：既存在双方错误放行，也存在无关修改被同时阻止。其防冲突能力尚不能替代明确分工、独立分支和人工检查。

本次新增的修复候选是 Windows 路径大小写归一化；仍然只记录问题，未实施修复。
